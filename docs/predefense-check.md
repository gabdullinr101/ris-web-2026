## 4. План демо - 7 минут

Запись для демо создаётся заново; её `id` записать на листке.

**0:00-0:30 - контекст.**
«Заказчик - семейный фитнес-клуб. Главный объект - запись клиента на тренировку. Покажу путь: администратор создаёт запись и назначает тренера, тренер подтверждает тренировку».

**0:30-4:30 - основной путь, один id.**

1. Вход `admin` / `Fitness2026!`.
2. «Создать»: «Персональная тренировка, силовая», зал 1, описание → «Создать».
3. Network: `POST /api/bookings` → **201**, в Response `id` и `number`. Назвать `id` вслух.
4. pgAdmin: `SELECT id, number, title, status, assignee_user_id FROM bookings WHERE id = …;` - тот же `id`, `New`, тренера нет.
5. В строке выбрать «Илья Соколов» → «Назначить»: статус остался «Новая»; Network: `PATCH …/assignee` 200.
6. Выйти, вход `trainer`: в списке только его записи.
7. «Подтвердить»: «Подтверждена тренером»; Network: `PATCH …/status` 200; в pgAdmin повторить `SELECT` - `InProgress`, `assignee_user_id = 2`.

**4:30-6:30 - защита и сохранность.**

1. Выйти, вход `trainer2`: этой записи в его списке нет. Открыть Swagger (`http://localhost:5000/swagger`) в том же браузере - он идёт с той же cookie `trainer2` - и выполнить `PATCH /api/bookings/{id}/status` с `{"status":"Closed"}` → **403** «Менять статус может только тренер, назначенный на эту запись».
2. На клиенте «Выход» → «Выйти» (cookie удалена). В Swagger `POST /api/bookings` → **401**.
3. В терминале API `Ctrl+C`, снова `dotnet run`, войти `admin`, F5 - запись с тем же `id` на месте.

**6:30-7:00 - завершение.**
«Известный предел: зал вводится номером, а не выбирается из списка, - в списке дефектов D-01. Расписание слотов и абонементы - запас на ВКР». Остановиться, ждать вопросов.

Не начинать с установки, `npm install` и листания исходников.

## 5. Вопросы, которые зададут

| Вопрос | Ответ своими словами | Куда показать |
|--------|----------------------|---------------|
| Чем ИС не сайт кафедры? | Сайт показывает страницы. ИС ведёт процесс: у записи есть состояние, переходы и правила, кто что может, данные сохраняются и общие для всех. | матрица ролей, переходы статусов |
| Почему браузер не подключается к PostgreSQL сам? | Тогда пароль базы оказался бы у каждого посетителя, а клиент обошёл бы все правила сервера - тренер изменил бы чужую запись. Правила и доступ к базе есть только у сервера. | docs/architecture.md |
| Зачем два PATCH, а не «сохранить запись»? | Назначение и смена статуса - разные действия разных ролей с разными правилами: назначает администратор или управляющий, статус двигает тренер. Один общий PATCH пришлось бы проверять по каждому полю. | `BookingsController`, role-matrix |
| Почему название зала не пишут в каждой записи? | Это 3НФ: название хранится один раз в `halls`, в записи - ссылка `hall_id`. Переименовали зал - меняется одна строка, а не все записи. | `db/schema.sql`, `\d bookings` |
| Почему пароль не кодируют Base64? | Base64 - способ записать байты буквами, он раскодируется обратно за секунду. Нужен hash: односторонний, с солью - у четырёх одинаковых паролей в базе четыре разных hash. | pgAdmin: `SELECT login, password_hash FROM users` |
| Что сознательно не сделали? | Оплату, абонементы, расписание слотов, личный кабинет клиента, уведомления, CRM. Это граница семестра из ЛР1 и запас на ВКР из заявки. | docs/project-proposal.md, раздел 7 |
| Чем 401 не 403? | 401 - сервер не знает, кто ты (нет входа). 403 - знает, но тебе это действие нельзя. | Swagger без входа; `trainer2` |
| Где проверяют чужую запись? | В сервисе на сервере: `BookingService.ChangeStatus` сравнивает назначенного тренера с тем, кто вошёл (из cookie). Спрятанная кнопка - только подсказка. | `backend/Services/BookingService.cs` |
