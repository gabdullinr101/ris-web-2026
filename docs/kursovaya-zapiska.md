## 1. Анализ и требования

Заказчик - ООО «Аматус Фэмили Фитнес», семейный фитнес-клуб. Сейчас запись клиента на тренировку живёт в тетради администратора и в личных сообщениях тренеру: подтверждение теряется в переписке, расписания у разных администраторов расходятся, управляющий не видит, сколько записей у тренера и сколько отменено.

Система ведёт каждую тренировку как одну запись: вид тренировки, зал, описание, тренер, статус и человеческий номер `БР-…`.

Роли: администратор ресепшн (создаёт, назначает тренера), тренер (двигает статус только своих записей), управляющий клуба (видит все, назначает и переназначает). Кто создаёт, тот не меняет статус.

Граница семестра: запись, назначение, смена статуса, вход, хранение в PostgreSQL. За границей и в запасе на ВКР: расписание свободных слотов и защита от пересечений, абонементы, личный кабинет клиента, уведомления, интеграция с CRM / 1С, несколько филиалов, аналитика загрузки.

Три критерия приёмки:

| № | Дано | Когда | Тогда |
|---|------|-------|-------|
| 1 | администратор вошёл | заполняет вид (5-80), зал (> 0), описание (10-500), «Создать» | запись `New` с номером |
| 2 | есть запись `New` | администратор назначает тренера отдельным действием | тренер есть, статус `New` |
| 3 | назначенный тренер вошёл | переводит свою запись `New → InProgress` | статус «Подтверждена тренером»; другой тренер не двигает |

**Артефакты:** `docs/project-proposal.md`, `docs/lab-01-requirements.md`.

## 2. Проектирование и архитектура

Архитектура web-ИС семестра - три узла: Vue (`:5173`) → ASP.NET Core (`:5000`) → PostgreSQL. Браузер не ходит в базу: иначе клиент обошёл бы серверные правила.

Модель данных: `halls` (справочник залов), `users` (пользователи с ролью), `bookings` (главный объект). В записи хранится `hall_id`, а не название зала (3НФ). Четыре статуса `New`, `InProgress`, `Closed`, `Cancelled`; переходы `New → InProgress`, `New → Cancelled`, `InProgress → Closed`, `InProgress → Cancelled`. Назначение тренера и смена статуса - разные действия. `id` - машинный ключ, `number` (`БР-0001`) - человеческий номер.

**Артефакты:** `docs/architecture.md`, `docs/data-model.md` (ER-диаграмма), `docs/api-contract.md`, `docs/requirements-matrix.md`.

## 3. Клиентская часть

Vue 3 + Vite на JavaScript, vue-router. Экраны: список `/`, создание `/new`, вход `/login`; шапка общая и стоит снаружи `router-view`. Общий массив записей - в модуле `bookingsStore.js`, таблица получает его через props и сообщает о действиях событиями.

Форма создания проверяет поля до отправки (длины после `trim`, зал - целое больше 0), отправка через `@submit.prevent`, кнопка блокируется на время запроса. Все запросы идут через API-модуль на `fetch`; список показывает одно из состояний: загрузка, пусто, данные, ошибка; для отказов разные тексты (400, 401, 403, 409, 500, нет связи). Пользовательский текст выводится только интерполяцией `{{ }}`.

Семантика: `main`, `form`, `label` у каждого поля, `table`.

**Артефакты:** `frontend/src` (`pages/`, `components/`, `api/`, `router.js`), отчёты `docs/lab-03-frontend.md`, `docs/reports/lab-04.md` … `lab-06.md`, `lab-12.md`.

## 4. Сервер и программный интерфейс

ASP.NET Core Web API (.NET 8). Контроллер тонкий: принимает HTTP, вызывает сервис, переводит результат в код. Правила процесса и права - в `BookingService`, сервис подключён через DI. Вход и выход данных - через DTO: клиент не может прислать `id`, `status` или тренера при создании.

| Маршрут | Успех | Отказы |
|---------|-------|--------|
| `POST /api/bookings` | 201 | 400, 401, 403 |
| `GET /api/bookings` | 200, `[]` | 401 |
| `GET /api/bookings/{id}` | 200 | 401, 403, 404 |
| `PATCH /api/bookings/{id}/assignee` | 200 | 400, 401, 403, 404, 409 |
| `PATCH /api/bookings/{id}/status` | 200 | 400, 401, 403, 404, 409 |

Все ошибки - `ProblemDetails`. Неожиданный сбой: на сервере одна строка лога (операция, зал, тип ошибки), клиенту - 500 без stack trace.

**Артефакты:** `backend/Controllers`, `backend/Services`, `backend/Dtos`, коллекция `docs/api-collection/bookings.postman_collection.json` (24 запроса), `docs/reports/lab-07.md`, `lab-08.md`.

## 5. База данных

PostgreSQL. Схема в SQL (ЛР9): первичные и внешние ключи, CHECK статусов и длин, индексы по статусу, залу и тренеру, учебные данные во всех четырёх статусах, запросы с фильтром, `JOIN` и `GROUP BY`.

Сервер работает с базой через EF Core и Npgsql; имена таблиц и столбцов в `AppDbContext` заданы явно и совпадают со схемой ЛР9. Схема создаётся миграциями `InitialCreate` и `AddUserPasswordHashes`, они лежат в Git. Строка подключения с паролем - в user-secrets, не в репозитории. Доказательство: запись создана, API перезапущен, запись с тем же `id` на месте.

**Артефакты:** `db/schema.sql`, `db/seed.sql`, `db/queries.sql`, `backend/Data/AppDbContext.cs`, `backend/Migrations`, `docs/reports/lab-09.md`, `lab-10.md`.

## 6. Безопасность и тестирование

Аутентификация - вход по логину и паролю, cookie `fitness_auth` (HttpOnly, SameSite=Lax). Авторизация - по роли и по владельцу записи на сервере: без входа 401, чужое действие 403; спрятанная кнопка - только подсказка. Пароли - hash `PasswordHasher` из ASP.NET Identity (PBKDF2 с солью), не открытый текст и не Base64. CORS - только для `http://localhost:5173`. Описание `<script>alert(1)</script>` показывается текстом.

Тестирование: коллекция Postman покрывает успех и отказы 400, 401, 403, 404, 409 (34 проверки); три критерия ЛР1 пройдены на живом стенде с одним `id` в интерфейсе, Network и SQL.

**Артефакты:** `docs/role-matrix.md`, `backend/Auth`, `docs/reports/lab-11.md`, `docs/acceptance-check.md`, `.gitignore`.

Поставка - локальный стенд по `README.md`: подготовка (dotnet-ef, user-secrets, миграции, `.env`), запуск двух процессов, учебные логины, проверочный сценарий.

## Приложение А. Трассировка критериев

| Критерий ЛР1 | Где в UI | Запрос API | Где в БД |
|--------------|----------|------------|----------|
| 1. Создать | `/new`, форма → строка в списке, статус «Новая» | `POST /api/bookings` → 201 | `bookings`: строка с `status = 'New'`, `assignee_user_id IS NULL` |
| 2. Назначить | список: выбор тренера → «Назначить» | `PATCH /api/bookings/{id}/assignee` → 200 | `bookings.assignee_user_id` = id тренера, `status = 'New'` |
| 3. В работу | список под тренером → «Подтвердить» | `PATCH /api/bookings/{id}/status` → 200; чужой тренер → 403 | `bookings.status = 'InProgress'` |
